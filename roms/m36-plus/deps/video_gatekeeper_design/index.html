תכנון: מפענח וידיאו יחיד עם בדיקת אישור לפני ניגון (M36 Plus)

ממשיך את block_video_system_level.md. שם נחסמו שתי השכבות (קודקים מערכתיים).
כאן: במקום לחסום הכל, משאירים דרך אחת לוידיאו לעבור, ושמים עליה שומר (gatekeeper)
שבודק אם הקובץ מאושר, לפני שהוא בכלל מגיע למפענח.

שתי בעיות נפרדות, שתי תשובות

בעיה א: אפליקציות עם מפענח וידיאו עצמאי, שעוקפות את המערכת לגמרי

סרקתי את כל 202 האפליקציות ברום (לא רק מה שהן *מצהירות*, אלא בדקתי בפועל את חתימות

הפונקציות בתוך כל ספריית .so שהן נושאות, עם nm -D). נמצאו שתי אפליקציות אמיתיות

עם מפענח עצמאי:

אפליקציהספרייהההוכחה
preinstall/vlc.apklib/arm64-v8a/libvlc.soמכיל removeH264or5EmulationBytes (פענוח H.264 ישיר) ותמיכת Matroska/MKV מלאה

המשמעות: גם אם המפענחים המערכתיים ייחסמו לגמרי, **VLC ו-AmazonMusic ימשיכו לנגן

וידיאו, כי הם לא שואלים את המערכת בכלל. הפתרון היחיד האמין: להסיר את שתי

האפליקציות האלה מהרום**, לא לנסות "לתקן" אותן (תיקון ברמת הקוד שלהן דורש לפרק ולשנות

ספריית C++ שלמה, לא ריאלי). כלי הסריקה: tools/bundled_decoders.py באטלס, כדי להריץ

מחדש על כל רום עתידי ולתפוס אפליקציה חדשה שתתווסף.

בעיה ב: איך משאירים מפענח אחד "חי" עם בדיקת אישור

לכל האפליקציות הרגילות (לא VLC/Amazon) אין ברירה: הן חייבות לעבור דרך ה-API

הציבורי של אנדרואיד, MediaExtractor/MediaCodec. פירקתי את המחלקות האלה **ישירות

מתוך framework.jar של M36** (לא הנחה כללית על אנדרואיד) כדי למצוא את נקודת המעבר

האמיתית, היחידה, שכל הקריאות עוברות דרכה.

נקודת ההתערבות (מאומתת מהקוד של M36 עצמו)

MediaExtractor חושף 7 גרסאות עמוסות (overloads) של setDataSource(...), אחת

לכל סוג מקור (String, Uri, FileDescriptor, MediaDataSource...). פירקתי את הפשוטה שבהן:

// android.media.MediaExtractor.setDataSource(String path), מתוך framework.jar של M36
public final void setDataSource(String path) {
    nativeSetDataSource(MediaHTTPService.createHttpServiceBinderIfNecessary(path), path, 0, 0);
}

כל 7 הגרסאות מגיעות בסוף לאחת מכמה מתודות native* (nativeSetDataSource,

וכדומה). זו בדיוק נקודת התפר: שורת קוד אחת, בתוך updatable-media/framework.jar,

שאפשר להוסיף לה בדיקה לפני הקריאה ל-native.

התוספת המוצעת

public final void setDataSource(String path) {
    if (!VideoGate.isApproved(path)) {               // הקוד החדש
        throw new java.io.IOException("not approved"); // המשתמש רואה שגיאה, לא קורס
    }
    nativeSetDataSource(MediaHTTPService.createHttpServiceBinderIfNecessary(path), path, 0, 0);
}

אותה שורה, בהתאמה, בכל אחת מ-6 הגרסאות הנוספות וב-MediaCodec.configure/

native_configure (למקרה שאפליקציה מריצה decode ישיר בלי MediaExtractor).

VideoGate.isApproved(path), איך בפועל לבדוק "חתימה"

שתי דרכים, מהפשוטה למחמירה:

1. רשימת טביעות אצבע (מומלץ להתחלה). מחשבים SHA-256 לכל קובץ וידיאו מאושר

מראש, ושומרים רשימה בקובץ שמוטבע ברום (/system/etc/approved_videos.json,

רק root יכול לכתוב לו). isApproved() מחשב SHA-256 לקובץ שמנסים לפתוח ובודק

התאמה ברשימה. פשוט, אמין, אי אפשר לזייף בלי לשנות את הקובץ עצמו (ואז ה-hash

משתנה וייכשל).

2. חתימה קריפטוגרפית אמיתית (RSA/Ed25519). כל קובץ וידיאו מאושר מגיע עם קובץ

חתימה נלווה (video.mp4.sig), והמערכת מאמתת אותה מול מפתח ציבורי שמוטבע ברום.

חזק יותר (אפשר להוסיף וידיאו חדש בלי לשנות את הרום, כל עוד הוא חתום), אבל דורש

תשתית חתימה (מפתח פרטי אצלך, תהליך חתימה לכל קובץ).

המלצה: להתחיל באפשרות 1 (hash). עוברים לאפשרות 2 רק אם צריך להוסיף סרטונים

חדשים בלי לצרוב רום מחדש בכל פעם.

מה עוד לקחת בחשבון (כנות על המגבלות)

  • הקובץ עצמו צריך להיקרא פיזית כדי לחשב hash, כלומר יש עלות ביצועים קטנה בכל

פתיחת וידיאו (סריקת הקובץ פעם אחת). לא בעיה לקבצים מקומיים רגילים.

  • סטרימינג (URL): הגרסה setDataSource(Context, Uri, Map) יכולה להצביע על כתובת

אינטרנט. אי אפשר לחשב hash מראש לתוכן שמשתנה. הפתרון הפשוט: לחסום לגמרי מקורות

שהם http(s)://, ולאשר רק קבצים מקומיים/תוכן שמגיע דרך ספק תוכן מאושר.

  • MediaCodec ישיר: אפליקציה יכולה לעקוף את MediaExtractor ולהשתמש ב-

MediaCodec עם ByteBuffer-ים ידניים (למשל סטרימינג מותאם אישית). לכן צריך את

הבדיקה גם ב-MediaCodec.configure, לא רק ב-MediaExtractor, כפי שצוין למעלה.

  • זה תיקון ב-Java bytecode (כמו שעשינו ל-PackageManagerService): אחרי השינוי

ב-framework.jar, צריך למחוק את ה-boot.oat/vdex המתאימים (ART מקמפל את

הפריימוורק מראש בעלייה הראשונה; בלי זה הקוד הישן ימשיך לרוץ).

רמת ביטחון

נקודת ההתערבות (setDataSource, native_configure) ושמות המתודות: ודאיות,

פורקו ישירות מ-M36. היתכנות הגישה (hash-list / חתימה): גבוהה, עיקרון סטנדרטי.

לא נבנה ולא נבדק קוד בפועל. זה מסמך תכנון, לא תיקון מוכן.
